2:T1cad,<h1>DROGS read-only API</h1>
<p>Office users create keys in <code>/admin</code> → <strong>API keys</strong>. Keys are issued by DROGS and used by other servers to read DROGS data. They are not Cloudflare credentials and never grant database or storage administration access.</p>
<p>Choose a separate key for each connected app, a descriptive name, permissions, and a lifetime of 1–365 days or <strong>never</strong> (the UI offers 7, 30, 90, 365 or Never expires; a never-expiring key can still be revoked). The full key is shown only at creation. MySQL stores a keyed hash, public prefix and metadata. Office users can revoke keys. Removing the issuing email from <code>ADMIN_EMAILS</code> also disables its keys. Changing <code>SESSION_SECRET</code> invalidates all keys and login sessions.</p>
<p>This document is also published at <a href="https://kuriakecastle.org/docs/">https://kuriakecastle.org/docs/</a>.</p>
<p>Send requests to the same domain as the registration app:</p>
<pre><code>curl 'https://kuriakecastle.org/api/v1/registrations?year=2027&amp;limit=50' \
  -H 'Authorization: Bearer YOUR_DROGS_API_KEY'</code></pre>
<p>Keep API keys in the calling server's environment, not frontend JavaScript, URLs or public repositories. These endpoints do not use browser cookies and do not provide cross-origin browser access.</p>
<table><thead><tr><th>Permission</th><th>Endpoint</th><th>Data</th></tr></thead><tbody><tr><td><code>backend:read</code></td><td><code>GET /api/v1/backend/*</code></td><td>Complete application data as detailed below; also permits the limited endpoints. This is selected by default for new keys.</td></tr><tr><td><code>registrations:read</code></td><td><code>GET /api/v1/registrations</code></td><td>Submitted annual registrations, including pending/unclaimed records; names, role, email, phone, country, city, organization, denomination, bishop reference, status and portrait path. No drafts, birth dates, payment details or receipts.</td></tr><tr><td><code>rosters:read</code></td><td><code>GET /api/v1/rosters</code></td><td>Annual pastor list entries, including active/removed status, names, contact details, church and supervising bishop. No removal notes.</td></tr><tr><td><code>photos:read</code></td><td><code>GET /api/v1/photos?path=ENCODED_PATH</code></td><td>A signed URL for a portrait attached to a submitted registration. No draft portraits, unattached uploads or receipts.</td></tr></tbody></table>
<p>Registration/list endpoints accept <code>year</code> (defaults to current registration cycle), <code>limit</code> (1–100; default 50), and <code>after</code> (the preceding response's <code>nextCursor</code>). Responses are <code>{data: [...], year: 2027, nextCursor: "..."}</code>; <code>nextCursor</code> is null when complete. Keep the same year while paging. The portrait path returned by registrations must be URL-encoded when requesting a photo link. Photo responses are <code>{url: "...", expiresIn: 3600}</code>. Previously issued image URLs remain valid until their own expiry even if the API key is revoked.</p>
<p>Keys have a limit of 120 authorized requests per minute. Responses use <code>Cache-Control: no-store</code>. Errors are JSON with an <code>error</code> message: 401 missing/invalid/expired/revoked key; 403 missing scope; 404 unknown endpoint or inaccessible photo; 405 a write/delete method; 429 request limit; 503 provider/database failure. All POST, PUT, PATCH and DELETE operations on this API are rejected. Keys cannot be used to sign into the office, create keys, submit registrations or call internal action endpoints.</p>
<p>Apply <code>mysql/002_api_keys.sql</code> to an existing installation (or <code>npm run db:migrate</code>, which applies both migrations). The new table stores only API-key hashes and metadata. The underlying MySQL and R2 connections remain separate; photo links still require working Cloudflare credentials.</p>
<h2>Complete backend read access</h2>
<p>With <code>backend:read</code>, use these endpoints. All remain read-only:</p>
<table><thead><tr><th>Endpoint under <code>/api/v1/backend/</code></th><th>Contents</th></tr></thead><tbody><tr><td><code>registrations</code></td><td>Full stored registrations: drafts and submitted records, all form fields including birth dates, payment amounts/status, receipt paths, review information, and timestamps.</td></tr><tr><td><code>rosters</code></td><td>Full pastor list entries, including status and removal notes.</td></tr><tr><td><code>profiles</code></td><td>Full stored profiles.</td></tr><tr><td><code>users</code></td><td>Account IDs and email addresses.</td></tr><tr><td><code>history</code></td><td>All application audit entries.</td></tr><tr><td><code>media</code></td><td>All tracked uploads, including draft/unattached portraits and receipts: object path, owner, type, size and creation time.</td></tr><tr><td><code>media-url?path=ENCODED_PATH</code></td><td>A temporary signed link to any tracked upload, including receipts.</td></tr><tr><td><code>settings</code></td><td>Current registration year, years with registrations, and fee amounts.</td></tr><tr><td><code>reference</code></td><td>Organizations, denominations and reference bishops.</td></tr><tr><td><code>keys</code></td><td>API-key metadata, scopes, creator, expiry, revocation and last use; never full tokens or hashes.</td></tr></tbody></table>
<p>Collection endpoints accept <code>limit</code> and <code>after</code>. Registrations and rosters include <strong>all years by default</strong>, with optional <code>year</code> filtering. They return full stored JSON records rather than the limited projections of the original endpoints. Payments and review details are nested in registration records. Follow <code>nextCursor</code> until null, URL-encoding cursors and keeping the same filters. <code>settings</code>, <code>reference</code> and <code>media-url</code> are individual responses and do not paginate.</p>
<p>This access excludes authentication internals (passwords, OTPs, sessions and rate-limit hashes), environment variables and database/SMTP/Cloudflare secrets. It provides no SQL console, infrastructure administration, write, upload or deletion permissions. Existing restricted keys retain their scopes; issue a new key with <code>backend:read</code> to grant full application-data access.</p>
<p>The preserved older Supabase API documentation is in <a href="LEGACY_API.md">LEGACY_API.md</a>.</p>
<h2>Accounts and successful logins</h2>
<p><code>GET /api/v1/backend/accounts?search=EMAIL_OR_NAME&amp;page=1</code> returns account signup/last-login dates, recorded login count, role, office access and current-cycle registration status (50 per page, with total). <code>GET /api/v1/backend/logins?user=USER_ID&amp;before=CURSOR</code> returns successful email-verified login events, newest first, 50 per page. Omit <code>user</code> for all accounts. Both require <code>backend:read</code>. No OTPs or session credentials are exposed.</p>
<p>Office admins can also use <strong>Accounts</strong> in <code>/admin</code> to search accounts and view their login histories. Apply migration <code>003_account_activity.sql</code> before deploying this version. Existing accounts have unknown signup dates; historical login activity cannot be reconstructed. Tracking starts with this release.</p>6:X
